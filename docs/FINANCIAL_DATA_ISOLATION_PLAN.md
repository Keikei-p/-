# 営業実績アプリ：実績データ完全保持・金額情報分離設計（提案／未デプロイ）

> **重要**：本ファイルは設計資料のみ。Firestore・商品単価・件数・社員権限・既存実績・Security Rulesには変更を加えない。
> 対象Firebaseプロジェクト: `sales-management-cc116`
> 公開サイト: `https://nico-factory.web.app/`, `https://keikei-p.github.io/-/`
> 目的: Owner/Masterの明示許可がないメンバー・Leaderによる金額情報への直接アクセスをFirestore Rulesレベルで禁止し、既存の件数入力と履歴維持を両立する。

## 1. 現行コードで確認済みの露出経路
- `firestore.rules` の `/products/{productId}` は同一会社であれば読み取り可。単価 `revenue`, `pricingOptions`, `cashbackOptions` が含まれる。
- `/records/{recordId}` も同一会社であれば読み取り可。`results[].revenuePerUnit` および `totalRevenue` が含まれる。
- `/recordCorrections/{correctionId}` の `before` / `after` に金額履歴が含まれ、同一会社で読み取り可。
- クライアントの `getCurrentInputResults` と `calculateResultsTotals` は単価をフロントエンド内で扱う。
- UI表示マスキングとFirestoreフィールド単位の秘匿は同義ではない（Firestore Rulesはドキュメント全体への読み取り許可／拒否）。

## 2. データ保全原則
1. 現行の `products`, `records`, `recordCorrections`, `revenueGoals`, `users`, `companies`, `teams`, `goals`, `invitations` は**削除・初期化・一括書換・移行しない**。既存IDと履歴は維持する。
2. 新しい*公開用コピー*だけ追加する。元ドキュメントは金額を含む**非公開の正本**として保持。
3. 管理者の承認なく権限、価格、件数、日付、班履歴、ランキングの基礎データ、報告状態を変更しない。
4. 過去データからの匿名化コピーは read-only 抽出→検証→新コレクションへ追加のみ。元のデータを上書きしない。
5. Firestore書込回数・保存容量は新コピーの分増えるため、Spark無料枠を計測して上限前に停止する。

## 3. 新しい読み取り境界（例）
| 区分 | 参照先 | 内容 | 読み取り許可 |
| --- | --- | --- | --- |
| 非金額商材 | `publicProducts` | `companyId`, `productId`, `name`, `active`, `sortOrder`, 金額を推測できない不透明な `planId` | 有効な同一会社社員 |
| 件数・報告 | `publicRecords` | 元の実績ID, 日付, uid, 班, 場所, 商材/プランID, 件数, 合計件数, 報告状態（単価・金額・CB金額は一切含めない） | 有効な同一会社社員 |
| 金額閲覧ビュー | `scopedRevenueViews` | 必要な範囲の売上金額。単価情報は含めない | 明示的な売上許可＋対象班・期間条件 |
| 現行の金額入り正本 | 既存 `products`, `records`, `recordCorrections` | **現在の値を維持**。今後発生する登録のみ安全なサーバーが更新 | Owner/Master。Owner以外は売上かつ単価が明示許可された範囲に限定（必要なら正本は管理者だけに制限） |
| 既存 `revenueGoals` | 現行のまま | 売上目標 | Owner/Masterと明示的な売上許可者のみ（現行の班スコープも確認） |

**注意**：`CB5000` や価格入りプラン名・金額進捗率・金額順ランキングも間接漏洩となるため非金額ビューに載せない。無許可者には件数・件数順ランキング・非金額目標のみ表示。

## 4. 登録フローの変更（操作感を維持）
1. 社員は従来どおり日付・班・商材・件数を入力する。
2. ブラウザから直接「単価・総売上」を受信・計算しない。Firebase ID Tokenを添えて**件数だけ**送信する。
3. 秘匿情報を持つ信頼済みサーバー（候補：Cloudflare Workers Free）で、ID Tokenの署名・期限・issuer/audience、社員の `active`・companyId・チーム権限、商材ID・件数・重複・競合状態を検証する。
4. サーバーのみが非公開商品単価から金額を計算。元のID・日別班履歴・作成メタデータを保ちながら**新しい登録／正当な訂正のみ**現行の `records` を更新し、`publicRecords` も同時に最新化する。競合時は上書きせず失敗を返す。
5. 監査ログと再送時の冪等性キーを保持。途中失敗なら確定成功を表示せず、再実行できる状態にする。
6. ServerのFirebase管理用資格情報はSecretで管理し、GitHubやブラウザには書き込まない。Workerは独立の最小権限・最小APIとし、LINE通知Workerとは分離する。
7. 管理者の許可設定は必ず**サーバー側で再確認**し、ブラウザのフラグやロール名を信用しない。

## 5. リリース順序（過去データを守る）
1. main・本番Firestore Rules・対象コレクションの**変更前スナップショット／バックアップ**を取得できることを確認。バックアップが無料枠/権限で不可能なら安全性と費用を報告し、無理に切替えない。
2. エミュレータに匿名化したサンプルを投入し、メンバー／Leader／売上のみ許可／売上＋単価許可／Owner／Master／他社／利用停止のテストを作る。
3. 既存コレクションから金額抜きコピーを新コレクションに生成し、件数・日付・社員ID・班ID・旧ドキュメントID・報告状態の全件照合を行う（元の書き換えなし）。
4. クライアントを公開ビュー参照＋安全な件数専用入力へ改修。OwnerやMaster画面は既存の数値を維持。
5. 新旧URLへ先行配信し、古いアプリ・Service Workerのバージョンを検知して安全に再読み込みさせる。
6. Firestore Rulesを最後に変更し、金額入り正本の読み取りを未許可の全社員に対して**拒否**。旧UIのキャッシュからも閲覧不可であることを確認。
7. 本番読み取りテストで旧URL・新URLの件数と売上をOwner視点で比較。メンバー視点ではSDK直接読取が permission-denied と判定されることを確認。
8. 違反／件数欠落／入力停止の問題があれば**公開切替を中止**。ロールバックは検証済みコードとルールのセットで行う（再度金額が露出する単純なルール巻き戻しは不可）。

## 6. 解除不可の検証ゲート
- 既存 `products`/`records` の件数・金額・作成日時・単価・スナップショット・ID・履歴を**変更前後でハッシュ比較**。
- 社員／未許可Leaderが `products`, `records`, `recordCorrections` の生データを `get` / `list` で読めない（両ドメイン）。売上ON単価OFFでも単価を含む正本は読めない。
- 件数のみの `publicRecords` に金額・CB・価格文字列が存在しない。
- 売上ON・単価OFFは売上ビューのみ、売上OFFは単価ONでも金額の読み出し拒否。
- 外部会社・無効アカウント・偽造ユーザートークンはすべて拒否。
- 通常の件数登録、重複防止、日別班訂正、代理登録、報告状態、履歴、ランキング・進捗が従来と同じ結果。
- 金額・件数の照合が1件でも失敗した場合は本番ルール切替を停止。

## 7. コスト条件
- Firebase Cloud Functionsの導入はBlazeプランが必要になるため、無料プランのままでは採用しない。
- Cloudflare Workers Freeはリクエスト／CPU等の上限内で固定費0円を目指せる候補。本人認証・IAM連携実装、既存アカウントの無料枠とSecret設定可否は別途確認が必要。
- コピーコレクション・追加読み取り／書き込みによるFirestore無料枠消費増がある。**固定費0円は設計上可能、無制限無料ではない。**
