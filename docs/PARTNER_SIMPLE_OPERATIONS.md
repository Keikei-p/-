# 協力店：既存営業実績アプリ再利用の最小運用仕様（2026-11-01）

## 確定方針

自社アプリの「協力店」会社枠を利用する。協力店向けに別データモデルを新設しない。
協力店側は自社と同じ実績/ランキング/履歴の操作感を持つ、件数専用の既存 `partner-workspace.html` を再利用。
自社の売上・単価・既存全実績・Firestore原票とLINEには触れない。
協力店への売上/単価は **UI非表示だけでなく、サーバー・Firestore Rulesで拒否の実アカウント検証が必要**。

## 人員区分（新規のAuthアカウントを量産しない）

- **自社オーナー**：既存の招待リンクから協力店会社代表をメール宛で招待。協力店の会社/班を指定し、ログインする**リーダー/同行（旧member権限）**を自社側で選んで招待。システムロールは従来の `leader` / `member` のまま。
- **協力店代表/リーダー**：自分の会社/班の `addManaged` で、スタッフの氏名だけ登録（メール認証、アカウント発行、パスワード不要）。リーダーが本人に代わり件数登録・修正する。個人別実績に紐付く `partnerWorkStaff` は既存コレクションを使用。
- **メールなしスタッフ**：件数集計対象であり、ログイン権限を持つユーザーではない。自分でログイン/入力はできない。顧客・売上・金額にはアクセスしない。

## 画面と実績

- 自社：既存indexの「協力店」タブ、招待リンクタブをそのまま使う。
- 協力店：件数ダッシュボード、班別ランキング、個人別ランキング、商材別ランキング、班/スタッフ管理、日別履歴、既存の件数保存APIを再利用。
- 同行は従来の `member`（ログインするユーザー）として扱う。メールなしスタッフと混同しない。表示の別名だけ追加し、ログイン権限・Firestore schema/Rulesは変更しない。
- 修正は既存HTML２枚の案内/ロール表示と回帰テストのみ。

## 本番未解決のゲート

現行 `getPartnerWorkspace` / `managePartnerWorkspace` はサーバーで `partnerRelations.active===true && countSharingApproved===true` を検証する。
先に本番化した `approvePartnerQuickCounts` の件数専用承認はこれを有効化しない。
したがって会社招待承諾だけで班管理・名前だけスタッフ登録が使える**とは主張できない**。
旧来の本体承認は独立の安全審査（finance Rules/バックアップ等）を前提にする。画面だけで擬似的に「承認済み」と扱わない。
会社コードAPIは未公開、実アカウントでの招待→班員登録→件数→ランキング→金額原票拒否E2Eは未完了。
不正な環境変数変更・財務権限の拡大・データ初期化・暗黙の旧会社所属削除をしない。

## 受け入れテスト

1. 自社Ownerのメール招待が協力店会社へだけスコープされる。
2. 自社がリーダー/同行のロールを選び、招待先本人だけが承諾できる。
3. 本体承認済みの協力店リーダーが、メールなしスタッフを自分の班だけへ追加できる。
4. 同一日・同一担当者の修正は版番号と監査履歴を維持する。
5. 個人/班/商材ランキングがメールなしスタッフの保存件数を扱い、未報告を0と偽らない。
6. 協力店の実アカウントが自社の売上・単価・過去金額原票を読めない。
7. 自社売上・単価、LINE、過去実績、他会社の履歴が元のままである。

このドキュメントは仕様・コード検証時の基準であり、本番での全受け入れを証明しない。
