# 営業実績の年次アーカイブと将来の削除候補 — 安全仕様
更新日: 2026-10-29 / 対象: PR #104 / **実データの削除・移行・権限変更なし**

## ユーザー確定方針
- 旧GitHub Pages URLは今後の正式運用対象外。新公式URLのみをサポートする。
- 長期的に無料枠で運用するため、1年単位で「見やすいPDF」「明細CSV」「復元用原票JSON」をまとめて書き出す。
- **PDFをダウンロードしたという事実だけでは原本削除を絶対に許可しない。**
- 保管期限や契約上の保持義務、再計算、税務証憑、紛争・訂正対応を確認する。

## Firestoreの容量/件数
- 2,000件は保存ハード上限ではない。現行レコードは原則、会社ID＋ユーザーUID＋日付で1件に商材別件数をまとめる。
- Spark Standard無料枠の目安: 保存 1 GiB、reads 50,000/日、writes 20,000/日、deletes 20,000/日。これらは**全プロジェクト合算**、かつ索引とメタデータも容量に含まれる。
- 現実の保存可能総ドキュメント数/耐用年数は**Firestore Usageの容量・ドキュメントサイズ・読み取り・利用人数・他のコレクション**を見なければ確定不可。
- 読み取り回数が先に無料枠を超える場合がある。年度末の大量書き出しにも読み取りが発生する。

## 1年分エクスポートの作業
1. 年と会社を選び、対象年度を**凍結予定**として表示。進行中の年度や締め未完了年度は「削除不可」。
2. 月ごとに全レコードID・原日時・会社ID・UID・所属班スナップショット・商材別件数・保存単価・キャッシュバック区分・訂正監査ログを取得。抜けと重複・期間外・他社データ混入があれば失敗として中止。
3. PDFを「事業年報」「月別合計」「商材別」「班別」「個人別」「訂正履歴一覧」に分ける。過去保存単価と現在承認単価を混同しない。
4. 同じ対象スナップショットに対応する**CSV、型付き復元用JSON、manifest(SHA-256/年度/会社ID/件数/合計/取得日時/版)**を出力。PDFを原本とは呼ばない。
5. 2か所の別媒体へ保存し、両方から独立して再読込。JSON・manifestのハッシュ、レコードID集合、会社/年/月/班/人/商材別件数と保存売上、当時単価/CBの完全一致を判定する。
6. **本番とは別の**隔離Firestoreエミュレータまたはテスト環境へIDと型を保って復元し、全件読戻し。実本番への書込み・削除をしない。
7. **受領した保存ファイルが管理者本人の端末で復元可能かを実確認**。GitHubの架空データ復元テストだけでは不可。

## 将来の「削除候補」ゲート（本PRでは実装しない）
- 会社オーナーだけが「削除候補として申請」できる。自動削除OFFが初期値。
- 原本の2媒体保存＋ハッシュ・集計一致＋隔離復元PASS＋対象年度締め確定＋未解決の訂正/返金/請求照合なし、を全条件にする。
- 年度単位の**明示的な二段階承認**と対象会社・年度・実績数の再表示を必須にする。
- 削除前後でも過去年間グラフ・ランキング・資料がアーカイブに切り替わり、ゼロ件やゼロ円と誤表示されない設計が必要。
- 改ざん・削除禁止の監査ログに、承認UID・年度・原票IDマニフェストのハッシュ・実行結果を記録する。
- Firestore Security Rulesが歴史的recordsのdeleteを拒否している間は、**削除機構は無効**。管理者の承認だけでセキュリティ規則を無効化しない。
- その後も規定保存期間内の業務記録を単純に消すことは避け、必要な法令・契約・請求対応の確認まで物理削除を保留。
- データ削除は永久的であり、回復できないリスクを明確に表示。**ファイルの「保存成功」ダイアログだけでは許可しない。**

## 先に導入する安全な現実案
1. 旧年度は通常ダッシュボードからデフォルト非表示にして、現在の年度だけ読み込む（Firestore原本は残す）。
2. 年次PDF/CSV/JSON+manifestをオーナーがダウンロード、2媒体検証。
3. アーカイブから過去のランキング/売上資料を閲覧する機能を先に完成させる。
4. 本物の原本削除は別PRとして審査・リリース承認を得る。今は削除コマンド・Cron・TTLを絶対に追加しない。
