# 営業実績アプリ｜本番データを変更しない金額情報の厳格分離設計

対象: \`sales-management-cc116\` / 公開URL \`nico-factory.web.app\` と GitHub Pages 旧URL
状態: **設計のみ**。このファイルの作成だけでは実装・テスト・公開は行わない。

## 最重要要件
- 本番の \`products\`, \`records\`, \`recordCorrections\`, \`users\`, \`companies\`, \`members\`, \`invitations\`, \`goals\`, \`revenueGoals\` の既存ドキュメントは**編集・削除・再計算・上書きしない**。
- 保存済み件数、売上、単価（保存時スナップショット）、ランキング根拠、社員所属、班履歴、代理入力/訂正履歴を維持。
- 新規招待は Leader/Member に無関係に \`canViewRevenue=false\`、\`canViewUnitPrice=false\`。明示許可なしは金額不可。OWNER/MASTER 権限は維持。
- **閲覧 UI だけでなく Firestore/API レベルで権限なしの金額取得を禁止**する。旧URL・新URLどちらからも同じルール。
- Spark/無料枠優先。Cloud Functions の Blaze プランは勝手に有効化しない。既存のLINE通知 Worker に秘密情報を混在させない。SecretsはGitHubにコミットしない。

## 検査で確認した脆弱な読み出し箇所
1. \`match /products/{productId}\` は全社メンバーへreadが許され、\`revenue\` / \`cashbackOptions\` / \`pricingOptions\` を返す。
2. \`match /records/{recordId}\` もreadで \`results.*.revenuePerUnit\` / \`totalRevenue\` を返す。
3. \`match /recordCorrections/{correctionId}\` もreadで \`before\` / \`after\` の金額スナップショットを返す。
4. \`revenueGoals\` は権限依存で読めるが、新アーキテクチャ側でも迂回読みを確認する。
5. \`index.html\` は直接Firestoreから商材・実績を取得し、ブラウザで金額計算・トランザクション保存している。Rulesだけ先に変更すると、権限なしの実績入力が失敗する。

**Firebase仕様:** Firestore Security Rules はフィールド単位で読み出しを制限できない。原本のreadを閉じ、別ドキュメント/専用サーバー経由で安全なデータだけ返す。

## 推奨アーキテクチャ（既存の原本は手を付けず維持）
- **原本・金額保管:** 既存 \`products\`, \`records\`, \`recordCorrections\` はそのまま残す。セキュリティルールで金額閲覧が許可された管理者、または厳格なゲートウェイのみ読み取り。単価非許可者に原本read権限を与えない。
- **金額を含まない読み取り専用ビュー:** 新規 \`publicProducts\`, \`publicRecords\`, 必要なら \`publicRecordCorrections\` を利用。元ID、companyId、uid、teamId、date、件数、報告状態、商材ID、単価無し名称等だけ。原本の作成日時/IDに基づき照合する。機密フィールドの存在をテストで拒否。既存の原本は一切編集しない。
- **保存処理:** ログインユーザーが件数・報告状態を入力すると、専用の小さな認証済みゲートウェイがFirebase IDトークンの署名/iss/aud/期限を検証し、Firestoreの利用者/会社所属/停止・班・代理権限を毎回確認。値段をクライアントから受け付けず、サーバーで原本の承認済み単価と現在の修正ルールに基づいて計算する。原本と公開ビュー、監査履歴の整合が取れる原子的書込み/再試行・競合防止を設計する。
- **商材・ランキング表示:** 権限なしは公開ビューだけから件数・順位・日別/月別を計算し、金額は1円も受信しない。売上だけ許可した人にも単価・CB・個別単価を公開しない。総売上/件数から単価を推測できる少数データの表示範囲も別途確認する。
- **サーバーアクセス:** Cloudflare Workers Free の独立Worker等を検討。秘密鍵はCloudflare Secrets、署名・所属・role・companyId検証、厳格なルートごとの認可、no-store、秘密をログに記録しない、負荷制限を必須。既存LINE通知用Workerとは別の権限と運用にする。現在の契約/実使用量確認まで費用0円は確約しない。
- **新旧URL:** 片方だけでセキュリティを掛けず、両URLを同じAPI/Firestore Rulesの下で運用。古いキャッシュ済み画面でも原本データが読めない（安全側に失敗する）ことを確認。

## 安全な切替順序
1. **現況固定:** 既存原本のドキュメント件数とID、単価・件数・収益・班・訂正履歴について秘密を漏らさない形式のハッシュ/チェックサムを取得。実行可能なエクスポート方式を事前検討し、Blaze必須の有料バックアップを勝手に有効化しない。
2. **開発ブランチで実装:** 公開ビュー生成器、認証済みゲートウェイ、UI、Security Rulesを作成。Firebaseエミュレータ/隔離テストデータのみで検証。既存原本を変更しない。
3. **公開ビューの安全なバックフィル:** 原本からの読取＋新規ビューへの追加のみ。ハッシュ一致、参照件数一致、金額なしを全件検証。原本へのupdate/deleteは禁止。既存原本への変更が進行している間の差分同期の方針を決める。
4. **閉鎖を先に、UIとAPIを協調公開:** メンテナンス時間を決め、金額原本への非許可readをFirestore Rulesで拒否。両URLのコードを更新。古い端末では書込が失敗しても機密は漏らさない。検証失敗時に原本のread許可を開き直すロールバックは禁止。
5. **本番検証:** 権限なしMember、権限なしLeader、売上のみON、単価のみON、売上＋単価ON、Owner、Master、利用停止ユーザー、他社ユーザーを含めて、Firestore SDK/RESTとAPIの直接アクセスを拒否・許可テスト。実績保存、同日重複防止、代理入力、訂正、ランキング、LINE通知、iOS/Android/PCを隔離環境で検証。
6. **照合完了後に案内:** 実機認証、旧新URL、公開ビュー/原本の集計を検証し、原本の旧ハッシュと現在の該当記録が一致したことを確認。途中でテスト不合格なら社員への案内禁止。

## 受入条件（全て満たすまで「完全秘匿」と呼ばない）
- 未許可ユーザーによる Firestore \`products/records/recordCorrections\` 直接readがPERMISSION_DENIED。新旧両URL、キャッシュ旧版でもデータの直接取得不可。
- 公開ビュー/API応答/ダウンロード/ブラウザログ/表示DOM/キャッシュに単価、CB、売上、過去の修正金額が残らない。
- 未許可Leaderは全社・自班の金額ともに不可。明示ONの売上は会社・班スコープ、単価は独立許可に応じる。
- 既存ID・社員・実績・件数・単価・履歴・売上の変更ゼロ、または事前承認された新規の通常営業入力以外の変更ゼロ。
- 新規の件数保存・既存記録の訂正・報告状態・目標・未報告通知・ランキング・旧URLが以前と同様に動く。
- 無料枠、Worker CPU/リクエスト、Firestore read/write増加、セキュリティ秘密鍵の権限/漏洩防止を点検済み。
