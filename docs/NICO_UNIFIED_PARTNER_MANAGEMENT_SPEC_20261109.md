- **版数:** 1.0（ユーザー確定仕様）
- **基準日:** 2026-11-09
- **対象:** 自社営業実績アプリ／協力店アプリ
- **本番Firebase:** `sales-management-cc116`
- **本番URL:** https://nico-factory.web.app/
- **GitHub:** `Keikei-p/-`

## 1. 開発目的・絶対原則

1. 自社と協力店の**件数**を同一の自社管理画面で確認する。
2. 自社Ownerが承認済み協力店を選択し、**登録済み**担当者・日付の件数を訂正する。
3. 自社Ownerが商材単位で協力店への入力可否をON/OFFできる。
4. 自社＋承認済み協力店の件数を**個人別・商材別・会社別・班別**の4合同ランキングへ反映する。
5. 協力店UIは自社ダッシュボードの構成・操作感を再利用し、**金額関連機能を除外**する。
6. 自社の売上・単価・CB・過去実績を協力店からサーバー/API/Firestore Rulesレベルで遮断する。

**画面は自社用・協力店用の2種類。データ正本と件数集計の基準は共通。** 既存の売上・単価・CB・件数・履歴・会社所属・商品定義を削除・初期化・暗黙の移行・自動補正しない。自社Ownerは協力店のアカウントへ「兼務」「移籍」「代理ログイン」せず、元の自社Ownerログインを維持する。

## 3. 構成・既存正本の再利用

- 認証: Firebase Authentication（既存の承認済み認証経路）。
- 権限付き処理: Cloud Functions（Owner認証、共有承認、保存、訂正、商材設定、ランキング）。
- データ: Firestore。**同じ件数の独立した別正本を増設しない**。
- UI: Firebase Hostingのスマホ対応自社画面・協力店画面。
- 防御: Firestore Security Rules。金額が入ったドキュメントを協力店に直接読ませない。
- ランキング用投影・キャッシュは**正本から検証して生成する読み取り用途**であり、正本と混同しない。

| 保存先 | 用途 |
| --- | --- |
| `companies/{companyId}` | 会社情報 |
| `users/{uid}` | 本人の所属 |
| `companies/{companyId}/members/{uid}` | 会社別本人権限 |
| `partnerRelations/{partnerId}` | 自社と協力店の承認関係 |
| `companies/{partnerId}/partnerWorkTeams/{teamId}` | 協力店の班 |
| `companies/{partnerId}/partnerWorkStaff/{staffId}` | 協力店スタッフ |
| `companies/{partnerId}/partnerWorkEntries/{date}__{staffId}` | スタッフ別日次件数の正本 |
| `companies/{hubId}/partnerWorkCountDays/{date}/reports/{partnerId}` | 自社側の会社別日次報告（明細と照合） |
| `companies/{partnerId}/partnerWorkAudits/{auditId}` | 訂正追記監査履歴 |
| `companies/{hubId}/rankingProductVisibility/shared` | 公開ON/OFF設定 |
| `companies/{hubId}/rankingSkuMappings/shared` | 承認された商材ID対応 |
| 既存の `products`, `records` 等 | 自社の金額付き原票。無許可の協力店には非公開 |

日次正本の既存 `companyId`, `hubCompanyId`, `date`, `staffId`, `teamIdSnapshot`, `counts`, `totalCount`, `version` 等を維持する。件数は0以上の整数、商材合計と総件数は一致、会社・担当者・日付はサーバー照合。過去の班所属は記録時のスナップショットを使う。**未報告と0件報告を区別**し、表示だけのために空の日次行を新設しない。

## 4. 認証・権限

### 4.1 自社Ownerの検証条件

各管理APIで**クライアントのrole/company指定を信用せず**以下をサーバーで検証する。

1. IDトークン有効・必要な再検証成功。
2. アカウント無効化なし。
3. `users/{uid}` 有効所属。
4. 自社 `companies/{companyId}` 有効。
5. 自社 `companies/{companyId}/members/{uid}` 有効。
6. 本人が対象自社のOwner。
7. 対象協力店がこの自社に**承認済み・有効な関係**を持つ。

協力店側が使うAPIに、他社金額を返す経路を設けない。元自社Ownerのログイン・売上権限は維持し、協力店操作時に所属を変更しない。

### 4.2 権限行列

| 操作 | 自社Owner | 自社Leader | 協力店Owner | 協力店Member |
| --- | --- | --- | --- | --- |
| 自社金額の閲覧 | 可 | 既存の明示権限のみ | 不可 | 不可 |
| 全承認済み協力店の共有件数 | 可 | 許可範囲のみ | 他社分不可 | 他社分不可 |
| 登録済み協力店件数の訂正 | 可 | 初期OFF | 自社分は既存権限 | 原則不可 |
| 商材公開ON/OFF | 可 | 不可 | 不可 | 不可 |
| 班・スタッフ管理 | 可 | 承認範囲 | 自社分 | 既存の役割による |
| 合同ランキング | 可 | 可 | 承認済み公開範囲 | 承認済み公開範囲 |

### 4.3 Owner所属確認エラー

「自社オーナーの所属を確認できません」を一括表示せず、`AUTH_REQUIRED`, `EMAIL_UNVERIFIED`, `OWNER_NOT_AUTHORIZED`, `PARTNER_RELATION_MISSING`, `FUNCTION_UNAVAILABLE`, `DATA_SHAPE_INVALID`, `NETWORK_ERROR` を区別する。画面は安全な日本語案内、ログは**エラーコードとリクエストIDのみ**。トークン、パスワード、金額原票をログに出さない。

まず既存 `getPartnerWorkspace` の実レスポンスとOwner権限判定を検証し、既存APIで不足すると証明された場合だけOwner件数管理コンテキストAPIを検討。

## 5. UI契約

### 自社

既存メニュー・売上表示・入力画面は**削除しない**。入口はダッシュボード／実績管理／協力店管理／商材公開設定／合同ランキング／既存管理設定。

`/owner-partner-admin.html` の構成:

- 上: 自社と協力店の件数サマリー、日付切替、再取得。
- 中: 有効・承認済み協力店の会社カードをワンタップ選択。
- 選択後: 会社合計、班別、スタッフ別、未報告、登録済み件数の訂正。
- 下: 訂正履歴、班・スタッフ管理の入口。

会社A→B切替、日付切替、ログアウトでは前の表示データ・編集内容を破棄して**サーバーから再取得**。協力店の再ログイン不要。

### 協力店

自社のダッシュボードのデザイン・カード配置・操作感を基本共有し、件数、許可商材、班、スタッフ、履歴、合同ランキングを表示。**売上・単価・CB・利益・金額グラフ・金額目標は画面にもAPIレスポンスにも含めない。**

## 6. 件数入力とOwner訂正

### 6.1 協力店入力

既存 `submitPartnerWorkspaceCounts` を優先。サーバーで認証中の本人・会社・班・スタッフ権限、有効な会社間共有承認、日付、対象商材のON状態、既存版番号、件数整数・総件数一致を検証する。

### 6.2 登録済み件数のOwner訂正

既存 `listHubPartnerCounts` と `correctHubPartnerCounts` を再利用。

1. Owner本人認証と対象協力店の承認関係再検証。
2. **存在する担当者・日付の行だけ**取得し、現在件数と`version`を提示。
3. 訂正後件数、**必須の理由**、`expectedVersion`を受け取る。
4. トランザクション内でも権限・既存行・version・件数と集計の整合を再確認。
5. 担当者明細と会社日次合計を整合更新し、`partnerWorkAudits` に訂正前後・理由・実行者を追記。
6. 書込結果を再取得し、対象日・月のランキングキャッシュを無効化。

**禁止:** 会社全体の数字だけ直接上書き、他担当者の履歴削除、金額原票への書込、訂正APIで存在しないスタッフ・実績を新設。新規代理登録は別権限・重複防止・登録者記録を備えた別設計。

## 7. 商材公開ON/OFF

自社Ownerのみが商材ID・商材名・マスタ有効性・共有公開状態・会社別例外・設定版・更新者／更新日時を管理する。基本は自社共通ON/OFF、必要に応じて協力店別OFF。

| 状態 | 協力店画面 | サーバー入力 | 保存済み件数 |
| --- | --- | --- | --- |
| ON | 表示 | 許可（認証・共有承認も必要） | 自社共有／承認済みIDでランキング対象 |
| OFF | 通常入力では非表示 | **拒否** | **消さない／過去の履歴を改変しない** |

**公開ON/OFFは過去日付を含む現在のランキング表示・合計件数へ直ちに反映**する。OFF商材は会社別・班別・個人別・商材別ランキングと公開合計の全てから除外し、再ONで元の保存済み件数が再表示される。これは表示・公開対象の変更であり、元の件数・売上・CB・履歴は削除・再計算・移行しない。協力店入力の許可はサーバー側でも同じON/OFF設定を強制する。全体OFFが会社別ONより優先し、会社別OFFは追加制限のみ。

`rankingSkuMappings/shared` により**OwnerがID対応を承認**。名前の類似のみで統合しない。未対応は「未統合」と明示し勝手に別商材へ合算しない。

**SB光とAir:** 2026年11月中は既存の「SB光・AIR（旧合算・未分類）」件数をそのまま保持し、2026年12月以降の分離を別途検討する。既存の光・Air個別商材は独立にON/OFFし、旧合算件数と混ぜない。過去の未分類合算を推測で分割・再配分しない。新商材追加は固定9商材のAPI検証を含め、UI・スキーマ・API・検証・ランキングを一体で拡張する。

## 8. 合同ランキング

**個人／商材／会社／班の4種類が同じ正本件数と同じOwner公開ON/OFF設定を参照する。**

- 商材: 自社＋承認済み協力店、承認済み商材IDへのマッピングに従う。
- 会社: 自社＋承認済み協力店を会社IDで識別し、会社別件数を集計。日次会社サマリーとスタッフ明細を二重計上しない。
- 班: 自社各班＋協力店各班、保存時の`teamIdSnapshot`で計上。
- 個人: 自社社員＋協力店スタッフ、内部IDで識別。同名でも混同しない。
- 切替: **合同（初期値）／自社のみ／協力店のみ**、日別／週別／月別。
- 件数降順、同数同順位、0件だけで表彰なし、未報告に0件順位なし。
- 表示名は承認済み名称・ニックネーム。協力店への個人ランキングは初期**順位のみ**。公開件数の範囲は別権限。自社Ownerの管理画面は許可された内訳を表示可能。

スタッフ明細と会社日次サマリーを二重計上しない。会社日次は**明細整合チェック**に使用。1ページだけ・古いキャッシュ・不完全取得で順位を確定しない。件数保存・訂正・関係承認解除・商材設定・ID対応が変われば該当会社／日／月の集計を無効化。

公開前検証: 明細合計=会社合計、商材合計=総件数、承認会社のみ、非公開・未承認商材の混入なし、API/キャッシュに金額なし、欠落・途中失敗なら表示停止。

## 9. 既存APIの接続方針

| API | 方針 |
| --- | --- |
| `getPartnerWorkspace` | 既存共有件数／班情報の取得、Owner認証・応答契約をまず確認 |
| `submitPartnerWorkspaceCounts` | 既存協力店入力を維持し、商材OFFのサーバー拒否を追加 |
| `managePartnerWorkspace` | 既存の班・スタッフ管理を維持 |
| `listHubPartnerCounts` | Owner専用、配備・フラグ・実アカウントを別判定 |
| `correctHubPartnerCounts` | Owner専用登録済み件数訂正、version・トランザクション・監査 |
| `getOwnerProductVisibility` / `setOwnerProductVisibility` | Owner限定、バージョン管理 |
| `getOwnerReviewedSkuMapping` / `setOwnerReviewedSkuMapping` | 対応IDの取得とOwner承認 |
| `getVerifiedJointCountRanking` | 金額なしの合同ランキング、初期OFFから安全接続 |

正常、未報告、認可拒否、認証切れ、競合、機能停止、データ不整合、通信障害を契約として区別する。新APIを増やす前に、既存APIの認証・入力・応答契約を合わせる。認証なしへの情報公開・エラー詳細への秘密出力禁止。

## 10. 金額遮断・二重所属

協力店が以下の**自社金額付き原票**をGET/LISTできないよう、画面のみならず**Firestore RulesとサーバーAPIの双方**で遮断する。

- `products`
- `records`
- `recordCorrections`
- `revenueGoals`

同一メールを使用した協力店への所属切替・二重所属で旧自社履歴を削除しない。ただし**協力店として扱う有効な所属コンテキスト**で古い自社金額閲覧権限を再利用できる経路を閉じる。既存 `secondary-finance-read-fence.mjs` 候補は、Ownerや従来許可済み社員の閲覧、旧URL/PWAの件数入力が壊れないことをEmulatorと実アカウントで確認した後にのみ検討。Owner管理機能と所属切替は別機能。

無効化・権限剥奪・共有承認解除を新たなリクエストに反映。会社・班・スタッフIDは毎回サーバー検証。公開APIは金額なし**許可リスト型**応答。セッション切替時には他社の表示を消し、訂正履歴は追記型、公開キャッシュに金額データを保存しない。

## 13. リリース禁止事項・障害対応

- 既存売上／単価／CB／件数／ユーザー／会社所属／履歴の初期化・削除・無断移行・再計算は禁止。
- 元Functionsの一括上書き、全Hostingファイルの無条件再デプロイ、未承認Owner代理操作禁止。
- バックアップ**READYメタデータのみ**を復元成功と扱わない。金額Rulesの切替前に隔離復元と既存入力継続を検証。
- CI PASSだけで本番完成を宣言しない。部分配備・CLIエラー後は本番metadataを独立検査し、同じ操作を自動再試行しない。
- 手動切替・権限ゲートは `AGENTS.md` と `docs/SALES_SAFE_CUTOVER.md` を厳守する。

## 14. コストと運用

開発段階の承認済みFirebaseトライアル枠を利用可能。ただし完全な課金上限と見なさず、費用上限／IAM／課金設定を勝手に変更しない。Functionsは原則 `minInstances: 0`。必要な期間／承認済み会社だけ取得し、金額原票を画面ごとに全件走査しない。読み書き回数を測定し、有料バックアップ等の継続費用と無料移行可能部分を区別する。

## 15. 完成判定（全項目が実証された場合のみ）

- [ ] 自社Ownerが**1ログインで承認済み全協力店を管理**
- [ ] 協力店別・班別・スタッフ別件数を確認
- [ ] Ownerの登録済み件数訂正と監査履歴
- [ ] 商材ON/OFFがUIとサーバー双方で強制
- [ ] 自社・協力店の件数が正確に共有
- [ ] 個人・商材・会社・班の4合同ランキングが本番正常稼働
- [ ] 協力店から自社金額原票へアクセス不可
- [ ] 自社の売上・単価・CB・既存実績・所属・履歴を保持
- [ ] 管理バックアップ本体の隔離復元成功
- [ ] スマホ実機でログイン・入力・訂正・表示成功
- [ ] 公開後の整合性・権限・費用を確認

**最終決定:** NICO FACTORYの営業実績管理は「**2つの画面を持つ、1つの件数共有・管理システム**」。自社Ownerは自分の自社ログインで承認済み協力店を管理。協力店は許可商材の件数のみ入力し、ランキングは共通正本件数を利用。金額は自社側に閉じる。既存データを保護して段階的に本番接続する。
