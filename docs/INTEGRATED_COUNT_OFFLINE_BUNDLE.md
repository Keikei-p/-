# Existing count release bundle

`tools/production/prepare-integrated-count-release-bundle.mjs` prepares exact local bytes for review. It reuses the 65-source candidate verifier and the existing canonical Owner package constructor. It has no credentials, network, install, environment-change or deployment path. Historical release operators and their source gates are unchanged.

From the LF checkout, after the candidate source manifest and Owner source pins have been verified:

```text
node tools/production/prepare-integrated-count-release-bundle.mjs --prepare ROOT MANIFEST NEW_OUTPUT_DIRECTORY EXACT_CANDIDATE_HEAD
node --test tests/integrated-count-release-bundle.test.mjs
```

The output directory must be new and its parent must already exist. The tool never overwrites it. `EXACT_CANDIDATE_HEAD` is the operator's explicit review reference; the independent source hashes establish file identity. The tool does not claim that a supplied SHA was reviewed or signed.

The bundle contains three isolated Functions packages and their original config files. The six necessary existing targets are `getPartnerWorkspace`, `submitPartnerWorkspaceCounts`, `listHubPartnerCounts`, `correctHubPartnerCounts`, `getVerifiedJointCountRanking` and `setOwnerProductVisibility`, in their recorded codebases. Owner code is generated by the existing canonical constructor. Other exports already present in the two existing packages are retained as source bytes; they are outside the six-function update scope.

Hosting preparation contains 17 raw replacements/additions and their exact gzip upload bytes, a 46-path populate request, the unchanged Hosting configuration and the prior 33-path manifest. Existing 29 file hashes and the service worker are preserved. Uploads use level 9, zero gzip modification time and a normalized OS header byte. The report records Node/zlib/platform/architecture; the compressed stream is reproducible within that pinned runtime and must be reproduced or reviewed separately in any other runtime.

`file-inventory.json` allows every prepared file except the inventory itself to be checked. The writer also verifies an in-memory hash inventory before creating the directory. `review.json` names all unresolved approval and real-account gates. Configuration readiness or correctness of existing source counts is not inferred from successful packaging.

This closes the offline packaging step only. The existing Hosting version is a rollback reference, not proof of a tested rollback. Original Function source archives, transitive npm lockfiles, environment flag approval, real-account verification, genuine signatures and a signed narrowly scoped apply operator are still required. `safeToApply`, `releaseApproved` and `applyImplemented` remain false. `--apply` and `--release` fail before reading source or identity files.

Authenticated GET-only inspection of the two deployed settings source archives found the SKU setter store and controller identical to this candidate. The visibility setter has the public-catalog transaction and identical controller, but its store omits Unicode NFKC normalization for monetary labels. The existing regression rejects fullwidth monetary labels before any visibility/catalog/audit write. Updating that existing setter is therefore included; the other settings Functions are preserved. No source archive or credential was persisted and no production resource was changed.
