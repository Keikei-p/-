# 営業実績アプリ｜2,000件超対応 本番切替の安全条件（2026-10-29）

対象: `Keikei-p/-`、月別表示UI の [PR #125](https://github.com/Keikei-p/-/pull/125)。
**この文書とPRだけでは本番へデプロイされない。実データの削除・移行・書換えを一切行わない。**

## いまできたもの（開発版）
- ダッシュボード: 会社全期間の常時読取 → 選択月（companyId + date範囲）だけをリアルタイム読取。
- 月変更・ネット切断・権限エラー時、古い件数/売上/ランキングを確定値として出さない。
- 過去月の別日訂正はUID+日付で原本をサーバー確認、重複と不確定結果を禁止。
- 朝礼用／最終報告文は対象日の属する月をサーバー検証してから生成。未報告プレビューは**今日**の実績を別途確認し、読み取れない時に「全員報告済み」と表示しない。
- 年間グラフは明示的に年間表示を開く時だけ対象年を取得（現時点では年全件。費用/通信量面で改善余地あり）。
- `firestore.indexes.json` と `firebase.json` を開発版に準備。**indexデプロイは未実施**。
- 架空25,001件で欠落なし・旧月・別会社・通信失敗・遅延イベント・報告文の隔離テスト。

## まだ完成ではない理由
1. 月別 `onSnapshot` は**表示月の全ドキュメントを一度に読み込む**。全期間全件読取より負荷は減るが、**「1か月25,001件を500件ずつ分割読取」はまだ実装していない**。2,000件はFirestore保存上限ではない。
2. Firestore SDKの分割読取だけで期間全件の厳密な同一スナップショット保証を作れないため、金額を含む資料化/ランキングを「途中ページで確定表示」してはいけない。PR #102 にスナップショット固定のサーバー側分割読取コードがあるが、本番移行・費用承認は別。
3. 本番実データでのバックアップ2か所・隔離復元・売上/CB/商品/人/班/日付の原票一致は**未検証**（PR #104／#117は隔離された架空データの検証段階）。
4. 協力店がFirestore生データの単価・売上を絶対見られない Security Rules の本番確認未完了（PR #105関連）。画面で隠すだけでは不十分。
5. 新旧URL、PWA更新、実際のiPhone/Android、日常の入力/訂正/報告/戻る操作の実機確認未完了。自動LINE送信はこのPRでは稼働しない。

## 本番切替前の必須チェック（どれか欠けたら延期）
- [ ] ownerが本番Firestoreの**全会社**の `records`、`products`、`teams`、`users`、`goals`、`revenueGoals`、`recordCorrections` 等を、原文書ID・更新時刻・型・メタデータを保って2か所へバックアップ。権限外会社へのアクセス禁止。
- [ ] 2コピーそれぞれの SHA-256/件数/会社ID別・月別・人別・商材別・班別件数と売上、NURO CB区分と当時単価を突合。独立Firestoreエミュレータまたはテストプロジェクトに**隔離復元して読戻し**。本番データを試験的に上書きしない。
- [ ] 本番ルールを変更する前に「協力店は単価・売上取得不可／権限あるownerは取得可／旧URLは壊れない」を実認証で確認。
- [ ] `firebase.json` の索引参照と `firestore.indexes.json` の条件を確認し、ownerが**索引だけ**を構築。作成完了と失敗時の戻し方を記録。コスト発生があるなら事前承認。
- [ ] 変更前後で同じ年/月/商材・班を比較し、件数・表示売上・目標・報告文章が一致。特に旧月に異なる単価やCBがあるケースを含める。
- [ ] 2,000/2,001/25,001件を模した隔離環境で日付変更・読み込み中・再接続・複数ユーザー同時登録・夜間の通知を検証。月に極端な件数がある会社は大容量分割読取の導入前に切替しない。
- [ ] GitHub Actionsの「Sales App Validation」「Month-scoped sales history preflight」が緑、保護ゲートの承認ラベル `sales-production-reviewed` とリリース署名書 `docs/SALES_RELEASE_SIGNOFF.md` が管理者承認で揃う。
- [ ] ブラウザとPWA両方で旧URLと新URLを2端末以上で確認。Firebase Auth の許可ドメイン、新旧導線、古いJSのキャッシュを確認。
- [ ] 切替後に件数/売上の読取りだけで異常を監視。問題があれば**旧コードへ戻す**。原データや履歴の削除、スキーマ自動変換は絶対に実施しない。

## 無料運用上の注意
Firestoreは**1日2,000件の保存制限ではない**が、リアルタイム監視するドキュメントが多いほど読取回数が増える。料金見積りなしにBlazeへ変更しない。Spark維持中は読み取り上限、複合索引、年度末の一括エクスポート手段を必ず管理者確認する。

**結論: PR #125は開発版。利用中の本番アプリを勝手に新コードへ切替しない。**
