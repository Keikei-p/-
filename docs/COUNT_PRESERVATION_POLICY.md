# 営業実績アプリ｜件数・履歴の不変条件（本番保護ポリシー）

対象：`Keikei-p/-` / Firebase `sales-management-cc116` / 新URL `nico-factory.web.app` と旧URL `keikei-p.github.io/-/`

## 大原則

> 認証、単価、売上保護、画面軽量化、ランキング等を改修しても、**これまで登録された件数・実績履歴を削除・再生成・上書き・移行しない**。

ユーザーが許可した明示的な「実績訂正」を除き、次の項目は変更しない。Firebaseへの書き込みスクリプトで本番の値を読み替えて保存し直すことも禁止。

- `records` のドキュメントID、全ドキュメント数、`companyId`、`uid`、`date`、`teamId`、`teamNameSnapshot`、`memberNameSnapshot`、`workLocation`
- `records.results` のすべての商材行（商材ID、CBプラン、件数）、`totalCount`、`createdAt`、`updatedAt`
- `products` の既存ドキュメントID、商材ごとの件数との対応、商材名と現在単価（別途本人が変更を求めた場合を除く）
- `users` / `companies/*/members` のUID・班情報・過去の班移動履歴と当時の所属
- 各集計軸：会社全体 / 日別 / 班別 / 個人別 / 商材別 / CB別、およびこれらの組合せでの件数
- 新旧URLから同じFirebase本番プロジェクトに接続する互換性

現在単価による**表示だけ**の売上再計算は、保存済み `results` や `totalCount` を上書きしてはならない。CB金額を単価として推測してはならない。表示売上と保存売上を別の概念として記録する。

## 変更する場合の順番（必須）

1. 本番に対しては**読み取り専用**でID・件数・集計軸・バックアップの確認をする。本人確認やアクセス権が無い限り、実データの差分を推測で埋めない。バックアップの存在と復元の成功は別物。
2. 変更を `main` で直接行わず、独立ブランチの最小差分PRにする。販売データへの移行・削除・再計上コードを含めない。
3. `node --test tests/sales-regressions.cjs` の**件数不変テスト**、既存の販売検算、Firestore Emulatorの owner/leader/member/他社拒否テストを全件通す。
4. セキュリティ修正の場合、件数だけ取得できる経路と収益を閲覧できる経路を分離して設計し、新規登録・代理入力・報告・ランキング・過去の班履歴が動くことを確認する。既存 `records` を無断で分割・移動・削除しない。
5. 画面更新後に新旧URLを**読取りで**検証し、件数のスナップショットを比較する。本番でテスト実績の追加・削除はしない。
6. 破壊的な変更、データ移行、Firestore Rulesの本番公開は、復元可能性と署名・承認の確認前には実行しない。

## 不具合・未確認事項

- Firestore `records` / `products` の読取権限が同社会員に広く、画面で非表示の売上・単価を直接読める可能性がある。件数の表示維持と権限修正の両立にはデータ構造の検討が必要。
- `records` と `products` は現在物理削除できる。監査ログを伴う論理削除や復旧方法は未導入。
- 旧形式データやCB不明単価は、推測で一括置換しない。
- Firestore 7日間バックアップは設定画像上で有効だったが、対象DBの識別・別環境での復元テストは未完了。
- 公開済みRulesや自動テストの成功は**実際の本人アカウントの保存成功を意味しない**。

## 今回の安全な準備PR

変更対象は `tests/sales-regressions.cjs` と本ドキュメントのみ。**本番アプリ画面、Firestoreルール、Firebaseデータ、収益計算、ランキング、会社メンバー、ワークフロー設定を変更しない。** テストに使うデータは架空の値で、実UID・実データは使わない。今回のPRをマージしても本番データの書込は発生しない。
