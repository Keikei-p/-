# 営業実績アプリ｜協力店の旧商材をそのまま連携する簡単設計 v2.0

対象: Firebase `sales-management-cc116` / GitHub `Keikei-p/-` / 2026-11-18 現行main `b25bad747944c1aba3a18d2846a355b4fe74e496` に基づく設計のみ。

## 決定すること
**自社Ownerは普段使う「商材管理」で1つのON/OFFを操作するだけ。**
画面内で「協力店に公開」「旧商材連携済み」「過去件数」を確認する。協力店側での別承認や個別ログインを要求しない。既存のOwner認証・会社関係のサーバー確認は省略しない。UIの設定項目を増殖させない。

**大原則: 協力店がすでに入力した報告・獲得日・会社・班・個人・件数を一切書き換えない。** 自社商材との紐づけは参照用であり、元データの商材ID/名称を更新しない。自社の売上・単価・CB・原票は協力店に配信しない。

「協力店商材」タブを新しく増やさず、既存の商材管理内に折り畳める領域を置く。基本画面はON/OFFと状態だけ。会社別例外・未連携修正・監査履歴は「詳細」に収納。スマホ1列レイアウト。

## 旧商材9カテゴリの扱い（現行コードとの一致）
既存 `partnerSku01..09` / 原本 `partnerWorkCountDays` `partnerWorkEntries` を再利用。

| 既存ID | 既存の協力店名 | 連携方針 |
| --- | --- | --- |
| partnerSku01 | NURO | 自社の一致商材IDに安全な完全一致で自動候補 |
| partnerSku02 | SBMNP | 同上 |
| partnerSku03 | YMMNP | 同上 |
| partnerSku04 | YM純新規 | 同上 |
| partnerSku05 | SB光・AIR（旧合算） | **分離禁止**。既存の合算商材へだけ対応 |
| partnerSku06 | ウォーター | 完全一致なら候補 |
| partnerSku07 | つばさ・HTB | **つばさ電気と同一と決めつけない**。Ownerに1度だけ選択 |
| partnerSku08 | 太陽光・蓄電池AP | 完全一致なら候補 |
| partnerSku09 | U-NEXT | 完全一致なら候補 |

候補の自動作成は既存 `suggestUnambiguousOwnerSkuMappings` を使用し、候補が一意・公開ON・自社の有効商材・会社別許可範囲に入る場合のみ。曖昧・重複・名称不一致は必ず未連携として残す。**自動候補の表示と自動保存は区別**し、Ownerが押す1回の「連携を保存」をサーバーで監査する。

### 既存分の移行（データ移動は0）
1. 協力店の旧カテゴリの入力済み件数をそのまま残す。
2. 対応表 `companies/{hub}/rankingSkuMappings/shared` の `companyId + partnerProductId -> hubProductId` だけを確定する。旧件数の原票は書換えない。
3. 期間（日・週・月）のランキングとOwner件数一覧を、同じ正規化された商材IDで**再集計**して表示する。再集計は加算上書きではなく既存の実績1件を1回だけ読む。
4. 過去分は入力時の獲得日・班・スタッフを保ったまま集計できる。未連携時は「未連携の旧実績」に残し、件数を消去しない。
5. 間違った紐づけが分かった場合は対応表だけ訂正し、変更履歴を残して安全に再集計。原票は不変。

## ON / OFF / 未連携の意味
| 状態 | 協力店で新規入力 | 自社で過去件数を閲覧 | 合同ランキング（日週月） |
| --- | --- | --- | --- |
| ON ＋連携済み | 許可 | 許可 | 対象として集計 |
| OFF（紐づけ済み） | 拒否 | **過去件数は保持して閲覧可** | OFF商材は対象外 |
| ONだが要確認・未連携 | 安全停止／入力は許可しない | **未連携枠に保持** | 正しい商材が確定するまで対象外 |
| 自社商品を非表示（active=false） | 拒否 | 過去原票は保持 | 新規集計の公開対象外 |

OFFにしても入力済みの値を0へ書き戻さない。ONへ戻せば過去原票が再びランキング対象になる。元データの二重コピーは作らない。

## 既存API/正本の再利用
- `getOwnerProductVisibility` / `setOwnerProductVisibility`: 既存の自社商品一括ON/OFF・会社別例外の唯一のOwner操作。既存実装のバージョン検査は維持。
- `getOwnerReviewedSkuMapping` / `setOwnerReviewedSkuMapping`: 旧商材と自社商品IDの紐づけ。既存のOwner認可・監査・重複SKUガードを維持。
- `getPartnerWorkspace` / `submitPartnerWorkspaceCounts`: 協力店の件数取得・保存を再利用。サーバー側でON/OFFを検証し、不許可カテゴリの新規変更を拒否。
- `getVerifiedJointCountRanking`: 会社/班/個人/商材ランキングの正本。3社分も自社分も同じ集計規則。
- `rankingProductVisibility/shared`, `rankingSkuMappings/shared`, `rankingCountPublicCatalog/shared`: 金額を含まない商品カタログ・公開設定・旧商材対応の整合を保つ。必要な書込みは**1つのOwner操作で整合性保証**。各カテゴリを協力店3社に別画面で手動登録させない。
- `partnerRelations`: サーバーで会社とOwner関係を検証。協力店側の相互承認ダイアログを追加しない。
- Firestoreの金額原票 `products` / `records` / `recordCorrections` / `revenueGoals`: 協力店に公開しない、データ変更しない。

### 現在の難所 → 簡素化の実装順
A. **自社商材管理へ埋め込み**。既存の独立ページ `owner-product-publication.html` / `owner-partner-setup.html` を壊さず、既存Firebase bridge/パネルを商材管理内で再利用。通常はON/OFFだけ表示。
B. **旧商材一括紐づけ**。既存コードには全社の候補を順次保存する処理があるが、途中停止で一部保存になる。新しい一括処理はOwner認証・対象3社・バージョン・価格遮断・重複をサーバーで検証し、**全件成功か無更新**にする。明示的な「確認して連携」1回のみ。
C. **ON保存→即反映**。既存Owner保存の同一トランザクション中で公開カタログと対応表の整合を確定させ、必要な公開対象を正本から再計算。協力店入力可否とランキングが同じ「許可カテゴリ」判定を参照。ONだけで無条件に未連携を勝手に連携しない。
D. **旧実績の読取・表示**。過去データは読み取り専用のまま会社→班→スタッフと期間（日・週・月）で集計。重複チェックを実施。
E. **限定本番公開**。Owner正本データのGET-only監査、Emulatorの会社別・財務権限テスト、バックアップ復元検証、Functionsの対象限定配備、実アカウント入力、本人確認を経てフラグ切替・公開後チェック。

**本設計文書は実装・本番デプロイを行わない。** 現在のFunctionsフラグや本番会社別SKU対応件数は、本番読取監査で改めて確認する。

## 必須受入テスト
1. 既存の協力店3社が持つ旧9カテゴリ原票の件数・日付・班・担当者を、設定前後で完全一致させる。
2. 自社OwnerがNUROをON→正しい3社候補をまとめて確定→協力店が新規登録→自社件数と商材/班/個人順位が同時に更新する。
3. 既存の過去件数もその獲得日に計上する。日/週/月の合計が二重加算されない。
4. OFF→新規書込みをサーバーで拒否、過去原票を保持しランキング対象から除外。再ONでランキング復帰。
5. 1社だけの会社別OFFはその会社だけ停止。他社は維持。
6. `partnerSku05` 光/AIRは旧合算を維持し分割しない。
7. `partnerSku07` つばさ・HTBを、つばさ電気へ**自動一致させない**。Ownerの一度の判断が必須。
8. 未連携カテゴリは消さずにOwnerの「要確認」に表示し、ランキングへ誤計上しない。
9. 協力店の実アカウントで `products` / `records` の金額原票GET/LISTを拒否し、画面でも売上・単価・CBを表示しない。
10. 既存の商材削除（active=false）・復元、ログイン効果、実績入力、Owner件数訂正、監査履歴が退行しない。
11. 本番デプロイ前後で実績原票件数・売上・単価・CB・既存ランキング履歴は変化しない。

## 今回の境界
この設計は「既存商材・既存件数の安全な統合」に専念する。会社認証や金融ルールを緩めない。新機能を追加するためにDBを作り直したり、元データを移し替えたり、商材を削除したりしない。
