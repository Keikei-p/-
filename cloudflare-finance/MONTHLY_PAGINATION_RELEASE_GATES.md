# 営業実績アプリ：2,000件超への対応（2026-10-29）

## 現状と範囲

Firestore の **2,000件という保存上限は存在しない**。問題は、既存の本番 `index.html` が `recordsCollectionQuery()` に `onSnapshot` と `getDocs` を使い、会社の全期間の原本を読み込むこと。年月が増えるほど遅延・端末メモリ・Firestore読み取り回数が大きくなる。2,000件に達しても原本自体は消えない。

この開発PRは、既存の Cloudflare Finance Gateway（本番では有効化していない）の **オーナー月間件数概要** で使う読み取りを、全会社全期間取得から **指定月の範囲だけ**に変更した。Firestore REST `runQuery` に `companyId ==`, `date >= 月初`, `date < 翌月初` を組み合わせ、`date ASC, __name__ ASC` の順序とカーソルによって最大500件ずつ読み進め、全ページで同一 `readTime` を使用する。異常（権限外会社、他月、重複、欠落疑い、スナップショット変更、読み取り上限）時には**売上/件数の部分合計を返さずエラー**にする。

テスト用の架空データ25,001件で、合計件数と売上および全件・重複なしを検証。空月、2,000件境界、他社混入、前後月、並び違い、ページ欠落、スナップショット変更も検証。

## 本番切替の前に必須

1. 本番Firestore全件バックアップと独立環境での件数/会社/実績/売上/単価/班履歴の完全な復元照合。ここでは**実行していない**。
2. クエリに必要な `records` の `companyId ASC / date ASC` 複合インデックスをステージングで検証。インデックスが見つからなければ旧コードへの全件取得フォールバックは行わず、画面で明確にエラー表示する。実本番Rulesと新旧PWAの互換テストが必要。
3. **本番`index.html` の全期間読み込みはまだ残っている。** 月変更時の対象期間だけ取得するクライアント（Spark対応）、年次チャートの別集計、同日既存実績の登録・訂正の互換、古い日付の検索と並行保存、スマホでの表示、ページング・月跨ぎの欠損検証が未完成。したがって、このPR単独では本番アプリの読み込み速度は改善しない。
4. Cloudflare Gateway を有効化する場合はFirebase Spark/Blazeなどの料金・認証/Secrets・Cloudflare無料枠を確認し、明示的なコスト承認を得る。**無料枠だけで実現したい場合、Firestore Web SDKの月指定クエリをブラウザ側で段階導入する**。Gatewayの実装を理由にBlazeへ勝手に変更しない。
5. 公開前の保護ゲート/管理者承認を守る。未検証の `firestore.rules`、`index.html`、本番DB、実績原票、商材、単価、CB、班履歴、アーカイブには変更しない。

**このPRは本番未公開**。2,000件を理由に過去の記録を自動削除・移動・価格再計算することは絶対にしない。
